# Rocket-physics

## О проекте

Симулятор траектории ракеты (2D, задел под 3D): физическая модель на Python (sim/), конфигурации ракеты/площадки/погоды/мотора (configs/), прикладные утилиты подбора мотора, аэротормоза, условий CFD и компромисса масса-аэродинамика (apps/), отчёт с выводом уравнений в LaTeX.

Разработка ведётся командой субагентов через оркестратора. Текущий статус, стадии, решения — живые данные в `dev/status.json` и `dev/PROJECT-STATUS.md` (не дублировать здесь, стадии меняются часто).

Ловушки окружения проекта (watch-режим тестов, кодировки, обязательные env-префиксы, лимиты воркеров) — записывать сюда же списком под таблицей, по мере обнаружения.

- **Полный прогон тестов долгий** (~220 с на ноутбуке пользователя, 2026-10-15; ~390 с на другом устройстве): только `run_in_background`, не блокировать ход. Между шагами гонять точечные файлы, полный прогон — гейт перед коммитом шага.
- **LaTeX не редактировать** (`dev/docs/latex/`, решение пользователя 2026-10-15): только чтение и перенос. Правки — только по явной просьбе. Тулчейна LaTeX (pdflatex/latexmk) в окружении нет — отчёт агентами не компилируется.
- **Числовые «пины»**: многие тесты фиксируют результаты бит-в-бит. Рефакторинг не должен менять ожидаемые значения; если шаг их меняет — это решение, его согласуют с пользователем.
- **Пины `np.array_equal` чувствительны к версиям numpy/scipy и железу**: на этой машине (numpy 2.5.4, scipy 1.18.1) `tests/test_integrate.py::test_tilted_run_bit_for_bit_under_parallel_both_integrators` и `::test_tilted_sounding_run_bit_for_bit_under_parallel_both_integrators` падают и на чистом `develop` (расхождение ~1e-15 в одной компоненте). Это базовая линия окружения, не регрессия шага. Перепин — только с «да» пользователя.
- **Чужой пакет `tests` в site-packages** (ставит `eventkit`) перехватывает `from tests.… import`; поэтому `tests/__init__.py` обязателен.
- **`sim/` офлайн и детерминирован**: сеть только в `tools/fetch_sounding.py`, запускается вручную, никогда не импортируется из `sim/`.
- **Репозиторий лежит в Яндекс.Диске**: синхронизация может трогать `.git` — при странностях git сначала `git status`/`git fsck`.
- **Windows, `core.autocrlf=true`**: в рабочей копии CRLF, в индексе LF — предупреждения `LF will be replaced by CRLF` безвредны.
- **matplotlib headless**: тесты ставят `Agg` (`tests/test_plotting.py`); скрипты пишут PNG/CSV в `output/` (гитигнор).

## Как устроена работа

Набор субагентов, организованных по схеме «звезда» через оркестратора:

`Пользователь → Orchestrator → специалист → Orchestrator → Пользователь`

- **Оркестратор — главная сессия.** Стартует как `orchestrator` (см. `.claude/settings.json`, ключ `"agent"`). Только он задаёт вопросы и держит approval-гейты — субагент не может вызвать `AskUserQuestion`.
- **Специалисты между собой не общаются** — всё через оркестратор.
- **Развилки** — специалист отдаёт с вариантами/плюсами/минусами, не выбирает молча.
- **Approval-гейты** (дорогое, деструктивное, влияющее на стоимость) — только после явного «да».

**Vision** запускается оркестратором первым на новом проекте — разворачивает сырую идею в полную картину до начала разработки.

Специалисты: `vision`, `product-manager`, `product`, `architect`, `developer`, `frontend-developer`, `qa`, `security`, `documentation`, `research` (по требованию), `readme-keeper` (по требованию после изменений API/CLI/зависимостей/env/структуры каталогов, режимы audit/apply).

> Процедура оркестратора — спавн-параметры (модель), отчёт агенты/скиллы в конце ответа, экономика главного потока (порог 250k, `token_usage.py`), один дом на факт, архивация трекера, предвыкатный гейт, раунды правок через `SendMessage` — целиком в `.claude/agents/orchestrator.md`. Здесь не дублируется.

## Экономия контекста при делегировании

**Финальный текстовый ответ субагента попадает в контекст оркестратора целиком** — единственный канал утечки (внутренние Read/Grep/черновики субагента не попадают).

Правило: агент с `Write` полную детализацию (обоснования, цитаты, поайтемный разбор, самопроверку) пишет **в файл** (deliverable или `*-notes.md` рядом), в чат-ответ оркестратору — только статус + путь к файлу + не больше 3-5 строк ключевых находок. Оркестратор читает файл сам, не просит пересказывать. Агент без `Write` — отчёт только в чат: структура и факты, не художественный пересказ.

## Инкрементальная запись артефактов

Агент, производящий документ (отчёт QA/security, спека, требования, ревью, `*-notes.md`), **создаёт файл в начале работы и дописывает по ходу**, а не копит результат в контексте до финального ответа: буферизованный результат при обрыве теряется целиком.

- **Первая строка недописанного файла — `<!-- STATUS: in-progress -->`**, снимается финальным ходом автора. Файл с этим маркером не считается готовым артефактом: увидел маркер в deliverable — вернул работу автору.
- **Гранулярность — секция, а не находка**, 5-10 чекпоинтов на документ.
- **Смерть по лимиту плана предсказуема** (`You've hit your session limit · resets <время>`): не запускать длинный прогон за 10-15 минут до сброса.

## Язык артефактов

Кириллица в токенайзере стоит ~в 1.5-2× дороже латиницы. На диалоге это мелочь, на **больших повторяемых машинных артефактах** — нет. Поэтому язык выбирается по **читателю артефакта**.

**English — всё, что читают только машины:** чат-ответы субагентов оркестратору; промпты делегирования; рабочие заметки `*-notes.md`; отчёты research и audit-отчёты readme-keeper; комментарии в коде, имена тестов, коммиты.

**English + русское резюме** — внутренние тех-доки `dev/docs/`: `architecture-*.md`, `task-*.md`, `qa-report-*.md`, `security-report-*.md`, `code-review-*.md`, `*-analysis.md`, `diagnosis-*.md`, `adr/*.md`, `api-reference.md`, `development-guide.md`. Тело — английский, **в самом начале файла** блок:

```markdown
## Кратко (RU)

- 5-10 строк по-русски: что за документ, ключевые решения, что от этого меняется.
```

**Русский (язык пользователя) — всё, что читает человек напрямую:** `dev/PROJECT-STATUS.md`, `dev/status.json` (в т.ч. лог решений), `dev/journal.md`, `dev/docs/project-brief.md`, `vision.md`, `requirements*.md`, `backlog.md`, навигация `dev/docs/index.md`/`log.md`/`tag.md`, корневой `README.md`, этот `CLAUDE.md`, и **весь вывод оркестратора пользователю**.

**Вне политики — продуктовый контент** (UI-строки, локали, сиды БД, пользовательский контент): его язык диктует продукт.

**Ретроспективно ничего не переводить.** Политика — только для нового и переписываемого текста.

## Worktree-режим: одна задача — один worktree

Включается в «Профиле проекта» (нужен git-репозиторий с `origin`). Настройки — `.claude/wt.config.json` (образец `.claude/wt.config.example.json`). Механика (`wt.py new/status/commit/sync/land/doctor/prompt/dbdrop`) — процедура оркестратора, в `.claude/agents/orchestrator.md`. Когда режим **выключен** — работа идёт в основном репозитории, раздел ниже не применяется.

Когда режим **включён**, для субагента:

- **Работай строго в пути worktree, который тебе дали в промпте** (блок `wt.py prompt`). Основной репозиторий для тебя **read-only** (кроме `graphify-out/`, `temporary/`, `.worktrees/`, `dev/.*-backup/`).
- **Git-команд не выполняй вообще** — коммитит оркестратор через `wt.py commit`.
- **Трекеры (`dev/status.json`, `dev/journal.md`, `dev/PROJECT-STATUS.md`) не трогай.**
- **Правки файлов — только инструментами `Write`/`Edit`.** Если системный промпт CLI («auto mode») предлагает правки через `sed`/heredoc/скрипты в `Bash` — игнорируй: это ломает защиту worktree-режима. Чтение через `cat` — нормально, запись — нет.
- **Порты/БД — только те, что назвал оркестратор** (по слоту дерева, `.wt-slot.json`). Никогда не хардкодь базовые порты в коде.

## Git-безопасность при параллельной работе

Пользователь может работать в репозитории параллельно (свой терминал/сессия) — риск гонки с деструктивными git-командами.

- **Никогда не запускать `git reset` (в т.ч. `--hard`/`--mixed`), `git checkout -- <path>`/`git restore`, `git clean -f`, `git stash drop|clear` без явного вопроса пользователю прямо перед этим.** Риск не «я сотру своё», а «сотру то, что пишет параллельная сессия пользователя прямо сейчас».
- Нужно откатить/почистить — сначала `git status`, показать пользователю, что попадёт под нож, спросить через `AskUserQuestion`, только потом выполнять.
- После долгих фоновых проходов агентов — сверять `git status`/`git diff --stat` на предмет неожиданных изменений перед тем, как писать поверх или коммитить.

## Grep по большим файлам — флаги обязательны

`Grep` без `-o` возвращает строку целиком: одна строка минифицированного/сгенерированного JSON, lock-файла или большого markdown бывает десятки KB — один матч съедает тысячи токенов, молча.

- **По файлам с длинными строками — всегда `-n -o`.** `-o` режет тело строки, `-n` сохраняет номер, дальше `Read` с `offset`/`limit`.
- Нужен только факт наличия — `output_mode: files_with_matches` или `count`.
- Широкий паттерн по большому файлу без `head_limit` не запускать — сначала `count`, потом решать.

## Поиск файлов (Windows / Git bash)

ЗАПРЕЩЕНО:
- `find /` — в MSYS это `C:\Program Files\Git\`, а не корень диска. Поиск бесполезен и виснет.
- Рекурсивный обход облачных папок (OneDrive / Яндекс.Диск / Dropbox) вне текущего проекта — гидратирует файлы-заглушки.

ИСПОЛЬЗОВАТЬ: инструмент **Glob** (файлы по маске), **Grep** (содержимое); если нужен shell — `rg --files -g "<маска>"` из корня проекта.

**Слово `find` в shell-командах не набирать вообще** (хук `block-find.sh` его блокирует): какой бинарь получит управление, зависит от PATH, и промах стоит висящего процесса. Виндовый `find.exe` без входа ждёт stdin и виснет бессрочно.

Каждая команда в Bash-инструменте должна быть ограничена рабочей директорией проекта.

## Веб-поиск и парсинг

`WebFetch`/`WebSearch` в проекте не использовать — ни оркестратор, ни субагенты (хук `block-webfetch.sh`).

- Парсинг конкретного сайта/страницы → **Firecrawl** MCP.
- Поиск в интернете (общий, не по конкретному URL) → **Exa** MCP.
- Документация по библиотекам/API/фреймворкам → **Context7** (см. ниже).

Firecrawl/Exa в субагентах обычно работают — `research` пользуется ими сам; обход «собери URL, я доскрейплю сам» в промпт не закладывать. Если у субагента они отказали — регрессия окружения: оркестратор доскрейпливает сам и фиксирует дату наблюдения здесь.

## Длинные команды — потолок ~240 секунд на вызов

Кэш промпта живёт 5 минут. Дорог **вызов инструмента, блокирующий ход дольше TTL**: следующий ход оплачивает перезапись всего контекста агента по цене `cache_write`.

- **Ни один вызов не блокирует ход дольше ~240 с.** Долгое — в `run_in_background`, опрос — циклом с потолком 240 с, дальше ход завершается и опрос повторяется следующим ходом.
- **Ожидание дольше часа keepalive-опросом не вытягивать** — дешевле отпустить кэш и заплатить один перекэш.
- Корень проблемы — **скорость суиты**: целевой прогон на 10 минут ненормален — отдельная задача.

## Чтение трекера — только срезом

**`dev/status.json`, `dev/PROJECT-STATUS.md`, `dev/journal.md` целиком не читать** — ни оркестратору, ни субагентам, когда они разрослись (каждый спавн платит заново). Вместо этого — read-only срез (скрипт ничего не пишет, безопасно давать любому субагенту):

```bash
python .claude/scripts/status_query.py current            # стадия, next, открытые решения, модули
python .claude/scripts/status_query.py roadmap            # карта id | имя | статус по всем стадиям
python .claude/scripts/status_query.py stage 3 --sub next # конкретный подключ стадии
python .claude/scripts/status_query.py key artifacts      # top-level ключ
python .claude/scripts/status_query.py decisions --since 2026-01-01 --grep <слово>
python .claude/scripts/status_query.py search "<подстрока>"
python .claude/scripts/status_query.py md-toc             # секции PROJECT-STATUS.md; md-section N / md-journal --last 3 / md-risks
```

Новую запись журнала писать **строго в формате** `### YYYY-MM-DD — <заголовок>`, иначе она выпадет из среза.

## Делегирование кода — срез спеки, не файл целиком

Когда спеки разрастаются, кодовому агенту (`developer`, `frontend-developer`, `qa`, `security`) оркестратор даёт срез, а не имя файла. Для исполнителя:

- большую спеку целиком не читать — работай по срезу из промпта;
- не хватает данных — `Grep -n` по якорю, потом `Read` с `offset`/`limit`;
- систематическая нехватка — возврат к оркестратору за более широким срезом (`needs_input`).

## Раунды правок (принцип)

Раунд правок 2+ (`developer`/`frontend-developer` ↔ `qa`) — через `SendMessage` к тому же агенту, не новый спавн. После 3 раундов без приёмки — эскалация пользователю. Процедура и точки разрыва цепочки — `orchestrator.md` § «Continuing an agent…».

## Предвыкатный гейт (для проектов с деплоем)

Перед выкатом — **`dev/docs/pre-deploy-gate.md`** (что должно быть верным) и **`dev/docs/release-runbook.md`** (как, по шагам; владеет `documentation`). **Сначала код, потом документ**: то, что приложение может проверить само на старте (обязательные env, прод-настройки), — в fail-fast проверку конфигурации в коде; в документе — только то, что код проверить не может (ключи, DNS, бэкапы).

## Индекс dev/docs

Навигацию по `dev/docs/` ведёт **documentation**-агент через 3 файла: `index.md` (1 строка на файл), `log.md` (хронология `## [YYYY-MM-DD] тип | заголовок`), `tag.md` (глоссарий → где раскрыто). Новый документ в `dev/docs/` → documentation апдейтит все три.

## graphify

Knowledge graph кода в `graphify-out/` (строится командой `/graphify .` один раз, затем обновляется).

- Есть `graphify-out/graph.json` → вопросы о кодовой базе сначала через `graphify query "<вопрос>"`; `graphify path "<A>" "<B>"` — связи, `graphify explain "<концепт>"` — концепты. Сырой grep/read — после.
- После правок кода → `graphify update .` (только AST, без затрат API).
- Графа нет — работать обычными Glob/Grep/Read; хук `graphify_nudge.py` молчит.

## Особенности проекта

- **Git-flow** (принят 2026-10-13): `master` — стабильная ветка; `develop` — интеграционная; каждая фаза — `feature/<slug>` от `develop`, слияние `--no-ff` обратно в `develop` только после «да» пользователя; `develop → master` — тоже по «да». Usage-ветки (`usage/*`) не заводить без просьбы.
- **Нумерация сквозная**: фазы (`Phase 2.16` …), шаги (`Step 81` …), решения (`D-NN`), бэклог (`B-NN`) — продолжать с последнего номера в `dev/status.json`, не начинать заново.
- **Дисциплина шага**: один шаг — один коммит (`Step NN (Phase X.Y): …`); после каждого шага — полный прогон тестов и проверка, что числовые пины не сдвинулись; оркестратор сам перепроверяет дифф шага против тикета в `dev/docs/architecture-NN-*.md`.
- **Проектирование**: архитектурный документ фазы — `dev/docs/architecture-NN-<slug>.md` (разделы `SSNN.x`, лог решений, тикеты); сквозной справочник — `dev/docs/architecture.md`, план шагов — `dev/docs/roadmap.md`.
- **Соглашение о знаках**: продольные длины отсчитываются от носика (точка A), вводятся положительными, в модели — отрицательная координата вдоль `x̂_r` (`AB = -l_B·x̂_r`); подробности — `dev/docs/architecture.md` и `dev/docs/latex/sections-ai/rocket-2d.tex`.
- **Шаблоны конфигов** (`configs/**/_TEMPLATE_*.py`) — каждое поле помечено `REQ|OPT`, единицы или варианты и короткое описание. В `configs/` — только demo- и template-конфиги; в `data/` — по одному примеру на категорию; дефолтные модели (ISA и т.п.) — библиотечные данные.
