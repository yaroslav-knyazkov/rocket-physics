## Step 114 review (c7f8b91) — new work beyond the original QA scope

Self-driven code-review round, 5 claimed fixes. Reviewed each diff + `tests/test_step114_review_fixes.py` on their own merits (not against the original QA report, which does not cover these).

1. **I_sp/m_prop consistency check** (`configs/schema.py::assemble`). New guard: if a motor declares both `m_d`/`m` (propellant mass) and `I_sp` with a `motor_curve`, the impulse-implied burned mass `J/(I_sp*g0)` must not exceed `1.01 * m_prop`, else `ValueError` at assemble. Correct and well-targeted: this is exactly the "thrust continues after the mass floor" bug class the dynamics mass-floor clamp (Step 97) was built to paper over silently. Test `test_inconsistent_isp_fails_fast_at_assemble` uses an absurdly low `I_sp=1.0` and confirms the message names the motor, `I_sp`, and `m_prop`; `test_consistent_motors_still_assemble` is a necessary negative control (confirms `DEMO` and the `LARGE` synthetic motor both still assemble under the new check — i.e. no default-scenario regression). One existing test fixture (`tests/test_config_pieces.py::_mass_on_motor`, `I_sp` 180.0 -> 600.0) needed updating to stay consistent with the new check; the comment explains the arithmetic (`J=2062 N*s, m_prop=0.4 kg -> 600 s`), and the fixture is only used by mass-composition tests (`s0.m` wiring), not by anything that pins a flight trajectory on that I_sp value — **no numeric-pin risk** from this edit.
2. **C_mq flip under standard convention** (`sim/aero.py::_load_table`). A table's `c_mq` *column* is now flipped (`-C_mq_col`) when `cm_convention == "standard"`, mirroring the existing `C_m` flip, since a textbook `c_mq < 0` (damping) must become the code's `positive = damping` sign. Important: this only touches the table-column path; the scalar `Aero.c_mq` field (used by the constant/linearized models and as the table's column-absent fallback) is explicitly left **unflipped** by design, documented in a new code comment in `sim/params.py` and in the template doc (`configs/rockets/_TEMPLATE_rocket.py`): "CODE sign (positive = damping) regardless of `cm_convention`... the scalar is NOT flipped under 'standard' (a table's c_mq column IS flipped there)". This is an internally consistent, intentional asymmetry (the scalar field has no declared source convention to flip from), not a half-applied fix. Tests: `test_standard_table_flips_c_mq_column_and_damps_pitch` builds a throwaway `standard` table with `c_mq=-8.0` (textbook damping sign), confirms the loaded column is `+8.0`, then confirms via `aero_moment_y` that the damping moment opposes `omega` (`M_y * omega < 0`) — a real physical-direction check, not just a sign-of-a-number check. `test_code_table_c_mq_column_is_untouched` is the negative control. Adequate.
3. **Jorgensen edge guard** (`sim/aero.py::_validate_table_oob`). New check: both table alpha edges must be `>= 2 deg` in magnitude when `table_oob == "jorgensen"`, because the extension scales the edge `C_m` by `Z(alpha)/Z(alpha_edge)` with `Z = sin(2a)cos(a/2)`, which -> 0 as the edge -> 0, blowing up the scale factor. Mathematically sound (division by a quantity that vanishes at the origin). Test `test_jorgensen_rejects_near_zero_alpha_edge` builds a table with edges at ±1 deg and confirms `aero.validate` raises mentioning "2 deg". Existing Jorgensen-using tests (`tests/test_aero_fb.py`, `tests/test_aero_oob.py`, `tests/test_qa_phase217_m1.py`, `tests/test_step114_review_fixes.py`) all use edges at >= 10 deg (per the original QA report's Step 112 probe table), so this new guard should not regress any in-tree table — confirmed by the full-suite result below.
4. **Aero coefficients once per RHS** (`sim/dynamics.py`, `sim/forces.py`). Pure refactor: `derivatives()` now calls `aero.coefficients(...)` exactly once and threads the result (`coeffs`) into `aero_force_body` and `aero_moment_y` via a new optional `c=None` parameter (falls back to recomputing if not passed, so the public call signature of `aero_force_body`/`aero_moment_y` stays backward compatible for any caller that doesn't pass `c`). `aero.coefficients` is a pure, deterministic function of `(t, y, p, flow, hold, fb)` with no call-count-dependent state (the `_OOB_WARNED` set is idempotent — add-if-absent, so warning behaviour is unchanged whether called once or three times per step). Confirmed bit-identical by construction (same function, same inputs, called once instead of three times) — this is a performance-only change with no numeric-pin risk. Test `test_coefficients_evaluated_once_per_rhs` monkeypatches `aero.coefficients` to count calls and asserts exactly 1 per `derivatives()` call — directly verifies the claim. Minor style nit (not a defect): `sim/forces.py` lines `A_x =flow.q * p.aero.S * c.C_x` and `A_m =flow.q * p.aero.S * p.aero.d_ref * c.C_m` lost the space after `=` in the edit (cosmetic, does not affect behaviour; worth a follow-up lint pass, not worth a defect ticket).
5. **Flown-thrust T/W in sweep** (`apps/motor_selection/scenario_sweep.py::_tw_liftoff`, new `sim/thrust_curve.py::thrust_stand_array`). `_tw_liftoff` previously used the stand-thrust curve only (`thrust_stand`); it now uses a vectorised `thrust_stand_array` (confirmed bit-identical to the scalar function via `test_thrust_stand_array_matches_scalar_bitwise`, `np.array_equal` over 257 points with non-trivial `k_J`/`k_t`) and additionally adds the nozzle-exit under/over-expansion term `A_e*(p_ref - p_amb)` when `A_e != 0`, matching what the flown thrust (`thrust_curve.thrust`) actually produces. Default path (`A_e == 0.0`, which is every in-tree motor config I found) is untouched — the `if p.thrust.A_e != 0.0` branch is skipped entirely, so `_tw_liftoff` is bit-identical to the old behaviour for every existing scenario/motor in `configs/`/`tests/` (confirmed by grep: no `Motor(... d_exit=...)` or `Thrust(... A_e=...)` construction exists outside the new Step 114 test itself). `test_tw_liftoff_uses_flown_thrust_with_exit_pressure_term` checks both branches: with `A_e=1e-3` the result matches a manually-computed `thrust_curve.thrust(...)` peak to `rel=1e-12`, and with `A_e=0.0` it matches the legacy manual-loop-over-`thrust_stand` peak to `rel=1e-15`. One design nuance, not a defect: `p_amb` is sampled once from the *initial* state (`result.y[:, 0]`, the pad altitude) and held constant across the whole `[0, t_lim]` window used for the T/W peak search, rather than resampled at each `t`. For a rail/pad-exit window this is a reasonable approximation (altitude change over the few seconds before rail exit is small relative to a scale height), but it is an approximation worth knowing about if `t_lim` ever becomes a long burn on a site with no rail. Noting as an **info item**, not a defect, since no acceptance criterion specifies trajectory-following pressure.

No numeric-pin regressions expected from any of the 5 Step 114 changes for existing (default-valued) configs; all 5 have an explicit test that either shows bit-identity on the default path or is a genuinely new behaviour gated behind a non-default field (`A_e`, `table_oob="jorgensen"` near-zero edge, `I_sp` inconsistency, `cm_convention="standard"` + a `c_mq` column). This is consistent with D-110's "strict opt-in, no default-value changes without explicit approval" policy.

Both failures are the RK45 branch of the same `np.array_equal(r_rk45.y[:, -1], pin["y_final"])` assertion (lines 203 and 225 of `tests/test_integrate.py`); in both cases every pinned component matches exactly except one near-zero component that differs at the ~1e-15 level (e.g. `-1.970645868709653e-15` vs the pinned `-5.48172618e-15`) — not a trajectory divergence, a last-bit rounding difference.

**Assessed as a pre-existing environment issue, not a regression caused by `fc938c8`/`c7f8b91`:**

- `python -c "import numpy, scipy; print(numpy.__version__, scipy.__version__)"` -> `numpy 2.5.3, scipy 1.18.1`. CLAUDE.md's own trap list records these exact RK45 pins as rewritten 2026-10-15 "под numpy 2.5.4 / scipy 1.18.1 (D-77)" — the installed numpy here is **2.5.3**, one patch version behind what the pins assume. The trap entry explicitly warns that scipy's `RK45` path (unlike the project's own `rk4`) shifts at the rounding level between numpy/scipy versions.
- Both failing fixtures (`_TILT_PARAMS`, `_TILT_SOUNDING_PARAMS`) use `aero=Aero(model="linearized", ...)`, not `model="table"` — none of the cm_convention/Jorgensen/table-loader changes in either commit touch this code path at all.
- The one change in either commit that is structurally capable of touching this path is Step 114's "coefficients once per RHS" refactor (`sim/dynamics.py`, `sim/forces.py`). Read `sim/aero.py::coefficients()` in full: it is a pure function of `(t, y, p, flow, hold, fb)` (dispatch dict lookup + a deferred-import call to `control.aero_coeff_delta`, no mutable state beyond the idempotent `_OOB_WARNED` set, which this test's model never touches since it never goes out-of-table). Calling it once and reusing the result is mathematically identical to calling it three times with the same arguments; there is no mechanism by which this refactor could change a single bit of the RK45 trajectory.
- Only RK45 lines fail; the RK4 assertions in the same two tests are never reached (both tests fail at the RK45 assertion, which runs first) but RK4 is known bit-stable across numpy/scipy versions per the same CLAUDE.md note — consistent with a scipy-adaptive-solver rounding drift, not a code defect.

**Conclusion: this is very likely the already-documented numpy-patch-version pin fragility (D-77), triggered by the local environment having numpy 2.5.3 instead of the pinned 2.5.4 — not something introduced by Step 113 or Step 114.** I did not re-pin or touch the test (out of QA's write scope, and D-77 says re-pinning needs the user's explicit "yes"). Flagging to the orchestrator: either (a) pin numpy to exactly 2.5.4 in the environment, or (b) get the user's sign-off to re-pin `_TILT_PINNED`/`_TILT_SOUNDING_PINNED` RK45 values under numpy 2.5.3, whichever the user prefers. This is **not** blocking the Step 113/114 verdict below (neither commit's diff touches the affected code path), but it does mean the full suite is not currently 100% green on this machine for a reason unrelated to this review.

No other regressions: all Step 97-100/112 targeted tests, all of Steps 113/114's own new tests (`tests/test_qa_phase217_m1.py`, `tests/test_step114_review_fixes.py`), and `tests/test_config_pieces.py` (updated fixture) pass. The previously-known `tests/test_template_docs.py` failure (Step 102, out of scope, noted in the original M1 report) is now green (Step 102 landed cleanly before these commits).
