## 1. `apps/common/ensemble.py` shape vs ticket

`Dispersion` is a `NamedTuple(name, apply, draw, stage)` with `apply(obj, value) -> obj`, `draw(rng) -> value`, `stage: "scenario"|"params"` -- matches the ticket exactly. `EnsembleResult` carries `table` (structured numpy array, one row/sample), `dispersion_names`, `metric_names`, `percentiles`, `n_failed` property.

- **"scenario"-stage genuinely re-derives via `assemble`:** confirmed. `run_ensemble`'s step (1) threads every sample's `Scenario` through `d.apply(sc, value)` for all dispersions (both stages, in order) on the SAME object, then calls `assemble(sc)` exactly once per sample at the very end (ensemble.py:327-334). A `"scenario"`-stage dispersion (e.g. `airframe_mass`) uses `_apply_scenario_path` -> `_dotted_replace` directly on the `Scenario` tree (`rocket.airframe.m`), so the subsequent single `assemble()` call re-derives `Weight` from the new mass via `configs.schema.assemble`'s own `_weight_from_pieces` -- not skipped. A `"params"`-stage dispersion (`_apply_params_path`) instead stages the value into `Scenario.overrides` (`{"aero.cx_scale": 1.3}`), which `assemble` applies itself via `sim.params.replace`, in `assemble`'s own order. Both are exercised directly: `test_normal_path_scenario_stage_sets_the_nested_field_exactly` and `test_normal_path_params_stage_routes_through_scenario_overrides` (the latter asserts `assemble(sc2).params.aero.cx_scale == 1.3`, i.e. actually calls `assemble`, not just inspecting `overrides`). `test_scenario_and_params_stage_dispersions_compose_in_one_sample` end-to-end mixes both stages in one `run_ensemble` call and checks the resulting table. This is correct per the ticket -- "scenario" stage is NOT a shortcut that skips `Weight` re-derivation.
- **Windows-spawn-safety claim is real, not just asserted:** `_safe_evaluate` (the function actually handed to `ProcessPoolExecutor.map` via `functools.partial`) is a top-level module function, not a closure, so `functools.partial(_safe_evaluate, evaluate)` is picklable as long as `evaluate` itself is also top-level/picklable -- which the module docstring states as a caller contract, not something `run_ensemble` can enforce itself (Python can't introspect "is this picklable" cheaply up front; it would only surface as a `PicklingError` at submit time for a bad `evaluate`). Traced `tests/test_ensemble.py`'s own `evaluate` callables: `_eval_cx_scale` and `_eval_flaky_above_threshold` are both defined at module level (lines 47-55), not closures/lambdas inside a test function -- so the claim that the *tests* satisfy the contract is independently verified, not just asserted in a docstring. `test_workers_1_equals_workers_4` and `test_spawn_safe_process_pool_executor` both genuinely exercise the `ProcessPoolExecutor` path (`workers=4`, `workers=2`) with these top-level callables and both passed in my own run (see §6).
- One cosmetic-only inconsistency: the module docstring (line 66-68) says `run_ensemble` reports "`np.nanpercentile` points", but the implementation (lines 368-374) manually filters `~np.isnan` and calls plain `np.percentile` on the filtered array -- functionally equivalent to `np.nanpercentile`, never actually calls that function. Not a defect (behaviour is correct and tested: `test_result_shape_and_percentile_summary`), just a docstring/implementation naming mismatch. Flagging as **minor/cosmetic**.

- Same seed -> same table: `test_same_seed_gives_the_same_table` runs `run_ensemble` twice with `seed=42`, `workers=1`, asserts `np.array_equal(r1.table, r2.table)` on the WHOLE structured table (not just one column) -- non-trivial since the table also carries string `error` and int `sample` columns.
- `workers=1 == workers=4`: `test_workers_1_equals_workers_4` is genuinely non-trivial. It runs `run_ensemble` with `workers=1` and then a SEPARATE call with `workers=4` (same `seed=7`, same `evaluate`, same `n=8`), asserting `np.array_equal(r1.table, r4.table)` on the full table. Since `workers=4` on `n=8` samples genuinely spins up a `ProcessPoolExecutor` with 4 worker processes and splits the 8 tasks across them (verified by reading `run_ensemble`'s own code: `ex.map(fn, configs_list)` with `max_workers=workers`), this is a real cross-process-count comparison, not "the same path called twice" -- the reproducibility guarantee rests on step (1) (sampling + `Scenario` application) running entirely in the parent process before any worker is spawned, so which RNG stream backs which sample index cannot depend on how the independent, embarrassingly-parallel `evaluate` calls are later distributed across workers.
- Sample statistics match requested mean/sigma: `test_sample_statistics_match_the_requested_mean_and_sigma` draws `n=2000` samples from `normal_path(mean=2.0, sigma=0.3)`, computes the true standard error of the mean (`sigma/sqrt(n)`) and of the sample std (`sigma/sqrt(2*(n-1))`), and asserts both the drawn mean and drawn std are within 3 standard errors of the requested values -- a correctly-derived statistical tolerance, not an arbitrary epsilon.
- One failing sample is NaN + reason, not fatal: `test_failed_sample_is_recorded_as_nan_not_fatal` is genuinely non-trivial -- it uses `_eval_flaky_above_threshold`, which ACTUALLY RAISES `ValueError` for any drawn `cx_scale > 1.05` (uniform draws span `[0.9, 1.2]`, so some draws are guaranteed to fail and some to succeed across `n=40`). The test asserts both `failed.any()` AND `not failed.all()` (so the test itself would fail if the injected failure path were somehow dodging every draw, or if ALL samples failed and silently passed as a no-op), then asserts `np.isnan` exactly on the failed rows and NOT on the successful ones, and cross-checks `r.n_failed == int(failed.sum())`. This is a real failure injection, not just a happy-path check with an isolated exception-handling unit test elsewhere.
- Spawn-safe on Windows: see §1 above -- genuinely verified, not merely asserted.

No criterion from the ticket is covered only by a tautological or trivial test. Coverage is thorough; I found no gaps against the ticket's "Tests first" list.

## 3. `sim/aero.py` / `sim/atmosphere.py` guard literalness + bit-identity

Both guards are literal `if` statements that skip the operation entirely at the default value (not "multiply/add a no-op value"):

```python
# sim/aero.py:793-794
if p.aero.cx_scale != 1.0:
    base = base._replace(C_x=base.C_x * p.aero.cx_scale)
```
```python
# sim/atmosphere.py:126-127
if p.atmosphere.dT_K != 0.0:
    T = T + p.atmosphere.dT_K
```

At the default (`cx_scale=1.0`, `dT_K=0.0`) the body never executes -- zero extra floating-point ops on the default path, matching the ticket's stated intent, and ruling out even a theoretical `x * 1.0` rounding/NaN-propagation edge case (e.g. `inf * 1.0` would still be `inf`, so this distinction is mostly stylistic for `cx_scale`, but matters more for `dT_K` since `T + 0.0` IS the same value for any finite `T`, so bit-identity would have held either way here too -- the guard is still correct/intentional defensive style, just not load-bearing for correctness in this particular pair of operations). Confirmed via the `git diff` (no other lines touched inside `coefficients()`/`_isa_air_state()` -- the two guarded blocks are pure insertions, nothing upstream/downstream of them in the same functions was altered). Both defaults are independently exercised bit-for-bit: `test_cx_scale_default_is_bit_identical_to_the_legacy_flight` (full `run_sim`, `np.array_equal`) and `test_dT_K_zero_is_bit_identical_to_the_legacy_isa_tier` (`air_state(...) ==` at 5 altitudes, `NamedTuple` equality is exact dataclass-field float equality, i.e. bit-for-bit for IEEE-754 floats in Python's `==`). Both pass in my own run (§6).

## 4. ISA `dT_K` analytic check (independent hand-derivation)

Code: pressure `press` is computed from the ORIGINAL lapse-rate temperature (`T_b`, `L`, `H`) before the offset is applied; only AFTER `press` is finalised does `T = T + dT_K` get applied, and `rho = press / (R_D * T)` uses the now-offset `T`. This models "same pressure-altitude relationship, but the air at that pressure is uniformly `dT_K` hotter/colder than standard" -- physically the correct model for a launch-day temperature anomaly (as opposed to, say, a different lapse rate, which would also move `press`). Hand-derivation: holding `press` fixed and perturbing `T -> T + dT_K`, `rho_new/rho_old = T_old/(T_old + dT_K)` exactly, since `rho = press/(R_D T)` is a pure `1/T` relationship at fixed pressure. For `dT_K = +15` (hotter): `rho_new/rho_old = T/(T+15) < 1`, i.e. density strictly DECREASES -- matches the ticket's claimed direction. `tests/test_atmosphere.py::test_dT_K_offset_lowers_or_raises_density_by_the_isa_ratio` computes `expected_rho = base.rho * base.T / (base.T + dT_K)` independently from the `base` (dT_K=0) run and compares to the actual `hot.rho` at `rel_tol=1e-9`, parametrized over `dT_K in (15.0, -10.0)` and altitudes `(0, 2000, 11_000, 25_000)` m (crossing the tropopause at 11 km, where the lapse rate `L` changes sign/zeroes) -- confirms the ratio holds in BOTH layers of the ISA model, and also separately asserts `hot.p == base.p` (pressure profile untouched) and `hot.T == base.T + dT_K` (literal additive offset, not some other transform). This is a real, independently-derivable analytic check, not merely "a test exists and passes" -- I re-derived the same ratio by hand from the `rho = p/(R T)` ideal-gas relationship before reading the test's own formula, and they agree.

## 7. RK4-sampled 100-sample timing (independent, REAL measurements, not extrapolation)

This section matters for the D-116 decision ("do Step 104 [segmented RK45] only if the measured cost of the Step 105 ensemble at RK4 dt=5ms exceeds the D-116 threshold [~5 min]"). I did not just carry the developer's caveat forward -- I obtained direct measurements myself, and they changed the picture materially.

**First attempt, flawed, corrected:** my first script built `_rk4_sampled_cfg()` from the demo `Config` directly for the single-flight timing, but passed the UNMODIFIED demo `Scenario` (still `solver.method="RK45"`, the default) as `run_ensemble`'s `base` argument -- a `"params"`-stage `Dispersion` only overrides `aero.cx_scale`, never `solver.*`, so my first ensemble measurement was silently running RK45, not RK4-sampled, at all. Caught this myself by noticing the ensemble's per-sample cost (0.2-0.25s) was two orders of magnitude faster than my own single-flight RK4-sampled measurement (319s) -- an internal inconsistency that should never happen for the same workload. Fixed by baking `Solver(method="rk4", sample_rate_hz=20.0, dt=0.001)` directly into the `Scenario.solver` field used as `run_ensemble`'s `base`, confirmed by `test_normal_path_params_stage_routes_through_scenario_overrides`'s own documented mechanism (overrides only reach `Params`, not `Scenario.solver`).

**Full demo scenario (t_max=1200s, includes the ~860s canopy descent to ground, apogee ~5.95 km at t~29.6 s):** single RK4-sampled flight (dt=0.001, the field DEFAULT, not the design doc's dt=0.005 estimate) = **319.4s** (890,868 steps, t_end=890.9s). A REAL (not extrapolated) `run_ensemble(n=4, workers=4)` on this same scenario took 363.17s wall for all 4 samples run genuinely in parallel -- scaled to 100 samples/4 workers (25 sequential batches of 4): **~9079s (~2.5 hours)**. This is wildly over any threshold, and would be the number anyone gets if they ran a Step-105 ensemble on the demo scenario's OWN solver settings (`t_max=1200`) under RK4-sampled mode without manually truncating `t_max`.

**Ascent+coast-to-apogee only (`t_max=40.0s`, truncating before the parachute/descent phase -- the phase actually relevant to an airbrake/controller ensemble, since recovery descent has no brake authority question):** single flight = 11.28s (close in order of magnitude to the developer's reported 8.05s single-flight figure -- the gap is plausibly explained by a slightly different `t_max`/machine, not a different mechanism). A REAL, DIRECT `run_ensemble(n=100, workers=4)` (not scaled from a smaller batch) measured **301.83s (5.03 minutes)**, `failed=0`.

**This is the key finding:** the developer's own extrapolation (8.05s x 100 / 4 ~ 201s, ~3.4 min, explicitly flagged as "not a direct measurement, re-measure on a quieter machine") undersold the real cost by roughly 1.5x. My real, direct 100-sample/4-worker measurement on an equivalent ascent-to-apogee-truncated scenario lands at **5.03 minutes -- essentially AT D-116's own stated "~5 min" threshold**, not comfortably under it. Given D-116's own text ("do Step 104 only if ... exceeds ~5 min"), this is right on the boundary rather than clearly on the "skip Step 104" side the extrapolation suggested. I also independently confirmed Step 105's OWN stated acceptance criterion is unaffected: a REAL, direct `run_ensemble(n=100, workers=4)` under the default `RK45` solver (full demo scenario, descent included) measured **16.63s** -- different from the developer's 4.43s (machine/contention variance, same order of magnitude) but still comfortably "well under a minute," so Step 105's actual acceptance gate is independently confirmed regardless of the RK4-sampled/D-116 question.

**Caveat on my own number:** my 301.83s figure is itself sensitive to the exact `t_max` truncation choice (40.0s vs. the true apogee event at ~29.6s) and to `dt` (I used the field default 0.001s, not the D-116 design doc's dt=0.005s estimate, which would be ~5x cheaper) -- neither of these choices is specified anywhere in the ticket, the code, or (as far as I can tell from the repo) any committed developer note, since the RK4-sampled timing figure was reported to the orchestrator in chat only, not as a script or test in this diff. **Recommendation, not a decision I can make:** D-116 should not be closed on either the developer's extrapolation or my own single re-measurement -- both are informal probes against an unspecified "controller ensemble" shape. The actual Step 107/108 controller-design-loop ensemble (once it exists) should be measured directly once its real `t_max`/`dt` are fixed, since the answer visibly swings from "3.4 min, skip Step 104" to "~9000s, definitely do Step 104" depending entirely on how much of the flight is simulated -- a decision input this sensitive to an unstated parameter is worth flagging to the user before D-116 is finalized either way.
